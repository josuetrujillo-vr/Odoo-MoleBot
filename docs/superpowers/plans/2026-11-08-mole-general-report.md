# Informe de ronda 1: consulta general de Mole

Estado: prototipo funcional acotado; no se afirma soporte universal. Se atienden conteos en español sobre modelos de negocio instalados comprendidos en una política explícita, y filtro de igualdad por nombre escrito entre comillas. Los criterios no representados se rechazan para evitar respuestas que omitan filtros.

## Implementación

- `assistant_local/models/general_query.py`: descubre modelos de una lista transversal mantenida en servidor, comprueba su instalación y ACL de lectura, y descubre campos visibles mediante `fields_get`. La política excluye campos privados, sensibles, computados, no almacenados y de tipos relacionales/binarios. Los alias comerciales en español identifican modelos, no implementan una función por pregunta. El catálogo para inferencia solo expone modelos permitidos; una vista interna de la política detecta un modelo explícito sin ACL y devuelve denegación, incluso para el filtro de nombre.
- `assistant_local/general_query.py`: valida el esquema cerrado, campos, tipos, operadores y literales. El servidor vuelve a consultar el catálogo, verifica que el plan completo corresponda a una forma soportada de la pregunta y compila el filtro de igualdad al ORM. Nunca acepta SQL, Python, dominios, rutas relacionales, métodos o contexto del modelo.
- `assistant_local/mole_local.py`: reconoce formas acotadas de conteo y un filtro `con nombre "valor"`; llama recibe catálogo y candidatos, produce un plan JSON completo o `null` bajo gramática restringida y el servidor compara el resultado con los planes compatibles. La detección previa es intencionalmente conservadora: el modelo no tiene libertad de inventar un criterio ni el servidor elimina palabras no comprendidas. La lista de candidatos actualmente debe tener un solo elemento, por lo que la desambiguación y la interpretación amplia siguen pendientes.
- `assistant_local/models/inference.py` y `assistant_local_mole/models/discuss_channel.py`: la ruta general ya no depende de llamar primero al proveedor de vacaciones; también existe ruta para proveedor HTTP local con herramienta estructurada, sujeta a la misma validación en Odoo. Se conservan las rutas de vacaciones propio y por nombre. Las cifras proceden de `search_count` bajo el usuario, con `active_test=True` y compañías activas verificadas por Odoo. El texto distingue archivo cuando el modelo tiene campo `active`, informa compañías activas en el contexto y explica que las reglas determinan el alcance.
- `tests/run_general_odoo.py`: base exclusiva con patrón `assistant_test_[a-f0-9]{12}`, filtro exacto, filestore propio, HTTP y cron deshabilitados y SMTP bloqueado. Solo reutiliza bases con nombre válido y directorio propio existente.

## Límites y riesgos

La política cubre solo los modelos enumerados en código y depende de revisión antes de agregar otros. El modelo interpreta entre candidatos prefiltrados; no selecciona libremente entre varios modelos ambiguos, no pregunta datos de seguimiento y no interpreta filtros arbitrarios ni relaciones, fechas, agrupaciones, sumas o moneda. No está garantizado que cualquier forma natural en español funcione. Un nombre se compara exactamente, con el comportamiento de igualdad del ORM.

La ruta HTTP fue implementada pero no se ha verificado con un servicio real. No se ha probado una matriz completa de grupos de campos, todos los modelos de la política, consultas costosas y tiempos límite, ni salida malformada del modelo físico; las salidas malformadas se probaron con proveedor simulado. `search_count` no tiene un límite de tiempo propio. Los metadatos de modelo denegado se usan solo para informar la denegación, no se envían al modelo. Un modelo no instalado o desconocido sigue produciendo aclaración, mientras que un modelo de la política instalado sin ACL produce denegación.

No se usó sudo para datos de negocio, no se invocaron servicios externos ni comandos remotos y no se realizaron commits. Se requiere revisión independiente de seguridad y cobertura antes de desplegar.

## Ronda 2: robustez y más formas naturales

Se rechazaron explícitamente los identificadores de modelo que no son cadenas antes de buscar en la política; una lista o un diccionario devuelve `ValueError` y no `TypeError`. La ruta HTTP comprueba que la respuesta, la lista de llamadas, la función y sus argumentos tengan las estructuras esperadas; respuestas malformadas producen abstención. El transporte HTTP real sigue sin probarse con un servicio físico.

Se ampliaron las formas conservadoras a «¿Cuál es el número de contactos?» y «Cuenta los productos», además de las anteriores. La sintaxis sigue exigiendo que toda la pregunta corresponda a una forma reconocida y que cualquier filtro sea un nombre entre comillas. Esto amplía ejemplos, pero **no resuelve el hallazgo principal de interpretación general**: el servidor aún preselecciona un único plan compatible, y el modelo elige ese plan o `null`. No hay evidencia de desambiguación ni de interpretación amplia del catálogo; se mantiene la abstención para criterios no soportados.

## Ronda 3: avance pendiente de validación

Se sustituyó la gramática de un solo candidato por una gramática que permite al modelo seleccionar entre todos los modelos del catálogo con ACL, cada uno con conteo sin filtros y, cuando procede, filtro de nombre con el literal citado. El modelo recibe etiquetas, alias y campos permitidos; genera JSON o se abstiene. El servidor conserva un verificador independiente: solo ejecuta si el plan propuesto coincide exactamente con la única interpretación reconocida de la pregunta. Por tanto, la selección de modelo ya es real, pero la ejecución continúa limitada por un verificador de sintaxis conservador; la interpretación amplia sigue sin demostrarse.
