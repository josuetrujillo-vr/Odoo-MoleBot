# Consulta general de lectura de Odoo

El usuario quiere preguntar por temas variados según módulos y permisos, sin addon o función por pregunta. Contactos es solo un ejemplo. Implementa un primer motor genérico extensible y verificable, conectado a Discuss y al backend local, sin pretender soporte universal.

## Requisitos

1. En el addon base existente, descubre modelos instalados y campos visibles para el usuario autenticado mediante Odoo; intersecta con una política de seguridad mantenida en el servidor para excluir modelos técnicos, datos especialmente sensibles, campos restringidos, binarios y campos computados con privilegios elevados. La política es transversal y ampliable, no una función por pregunta. No uses sudo para obtener datos. ACL, reglas, grupos, compañía y campos se revalidan al ejecutar.
2. El modelo propone un plan declarativo acotado, nunca SQL, Python, dominio Odoo, rutas relacionales libres ni nombres de métodos; el servidor valida claves, identificadores, tipos, operaciones, filtros, literales y límites, y compila con ORM. Una implementación inicial puede limitarse a conteos y filtros simples, pero debe funcionar para más de un modelo instalado sin implementación específica por pregunta y dejar clara la cobertura. Filtros inventados o sin respaldo textual se rechazan; información insuficiente o ambigua produce pregunta aclaratoria.
3. En el backend local de Windows de este proyecto, implementa interpretación efectiva del catálogo para consultas variadas con salida estructurada validada; el proveedor simulado sirve para pruebas adicionales, no sustituye prueba con modelo real. Texto y números de respuesta salen de Odoo y no se confía en texto numérico libre del modelo. Si la calidad del modelo no basta, abstenerse; no afirmar comportamiento universal.
4. Usa entorno real del usuario, compañías autorizadas y reglas; distinguir cero, error y falta de permiso. Explica que se cuentan registros activos visibles, compañía y criterios. No incluir agregaciones monetarias ni sumas sin semántica explícita de moneda/unidad/signo; proteger modelos sensibles. Rechazar salidas malformadas, inyección, campos privados, operaciones no permitidas, literales no presentes, recursos excesivos y contextos que amplían permisos.
5. Prueba TDD: al menos dos modelos de negocio instalados, usuarios con diferentes permisos, regla de registros, distintas compañías y compartidos, archivados, cero frente a denegación, campo privado, inyección, petición ambigua, salida inventada y modelo indisponible, flujo Discuss sin mocks de capacidad, y al menos una prueba de modelo real con datos sintéticos. Todo solo local, sin correo externo, base `assistant_test_[a-f0-9]{12}` exclusiva y filtrada, no VPS. Protege y conserva flujo vacaciones propio y ajeno. No uses nuevos addons por pregunta.
6. Documenta capacidades y límites reales. No hagas commits ni despaches agentes. Escribe informe detallado con archivos, pruebas RED/GREEN y límites en `docs/superpowers/plans/2026-11-08-mole-general-report.md`. Si el modelo local no puede cumplir el contrato con evidencia, conserva una solución segura que informe la limitación y repórtala sin afirmar que está terminado.
